# B5. Kill switch for the MAIN-world page hooks (Phase B; old ref P13)

**Why.** `apps/browser-extension/src/entrypoints/content/page-hooks.ts` wraps `History.prototype.pushState` and `replaceState` in the page's own world at `document_start` on every page and frame (installed via the console bridge). It is carefully written, but a page can observe the change and the user cannot turn it off. The manifest declares `frame-responder.ts` (ISOLATED, all frames, `match_origin_as_fallback`), `index.tsx` (ISOLATED UI, top frame) and `console-bridge.ts` (MAIN, `document_start`, all frames). The build uses `@crxjs/vite-plugin`, so script file names are hashed, and a static content script cannot read extension storage before it runs.

**Do.** Add a setting "Track client-side routing and capture console output from page load" (default **on**) with an optional excluded-sites list. Implement it by **registering the MAIN-world console bridge dynamically** with `chrome.scripting.registerContentScripts` (`excludeMatches` from the list, `persistAcrossSessions: true`), reconciled on install, update, startup and settings changes; resolve the hashed script path at runtime from the built manifest; remove it from the static manifest only if the build allows it cleanly. If dynamic registration is incompatible with the build, say so in `REVIEW.md` and implement the narrower fallback (static script, excluded-site list enforced inside it through a page-readable attribute set early by the ISOLATED responder; document that the first load of a newly excluded site may still be hooked). Document the compatibility note and the switch in `TROUBLESHOOTING.md`.

**Tests.** e2e: with the setting on, console output from page load and `pushState` counts still work (the existing `core-tools` and `dom-health-routing` tests pass unchanged); with the site excluded, `history.pushState.toString()` is native, hook events are absent, and DOM Health reports routing evidence as unavailable with a reason.
