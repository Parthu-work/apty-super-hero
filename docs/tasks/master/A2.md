# A2. Apply the deny list to Apty Client response bodies (Phase A; old ref P04)

**Why.** Page capture honours the opt-in and deny list (`isUrlDenied` in `apty/network-capture-session.ts`, `settings.networkBodyCaptureDenyList`), but `inspectResource` in `apty/extension-network-inspector.ts` (about line 686) calls `provider.getResourceBody(best.requestId)` (about line 776) without consulting settings. The user's explicit request ("get segments.json") is consent for that one resource; the deny list is the policy layer.

**Do.** Before `getResourceBody`, apply `isUrlDenied` against the same list. If denied: do not fetch, still return metadata, return `status: "body_denied"` with the matching pattern, the reason and how to change it; `get_evidence_json` must never expose a denied body. Update `packages/ui/src/components/settings/data-handling-card.tsx` copy (currently scoped to "page network capture") to say the list also covers Apty Client bodies; update the privacy statement under `docs/`; put examples (user-preference and identity endpoints) in the placeholder without changing the default (`[]`).

**Tests.** Unit for denied and allowed paths. e2e (`apty-client.e2e.test.mjs`): the fixture Client serves a `/…/<user-id>.json` preference body and `/…/segment.json`; with a matching pattern the agent gets `body_denied` and the Client's `get-resource-body` is **never called** for it; `segment.json` still returns in full; clearing the list restores the body.

**Acceptance.** A denied Client resource never reaches `get-resource-body`; allowed ones return in full.
