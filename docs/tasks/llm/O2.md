# O2: generic tool-result cap and pruning

Status: done (see REVIEW.md at the Phase A checkpoint). Tests: `request-budget.test.ts`,
`llm-outbound.e2e.test.mjs` (O2), harness `sent` table. Built into the chain by
`apps/browser-extension/src/hooks/outbound-filters.ts`.

New `browser-runtime/src/runtime/request-budget.ts`:
`MAX_TOOL_RESULT_TOKENS = 2000`, `FULL_RESULTS_KEPT = 4`,
`STUB_PREVIEW_CHARS = 200`.

- Cap any oversized tool result; exempt results that carry an `evidenceId`
  with an already-bounded preview.
- Stub (never the current turn's) results beyond the last 4 full ones to
  `{tool, size, evidenceId?, first 200 chars}`.
- Never break function_call / function_call_result pairing.
- Runs as an outbound filter (O1), after sanitizing.
- Tests: cap boundary, stub shape, current turn untouched, pairing intact,
  evidence exemption; red-green; measured before/after from the harness.

## As built (differs from the spec text; the owner confirmed both points)

- A JSON result is never cut into invalid JSON. It is shrunk in rounds
  (long strings, then long arrays, then deep objects, then keys of nested
  objects) until it fits, keeping top-level keys and scalars; it carries
  `truncatedForModel: {originalChars}`. Only text that is not JSON, or JSON
  that cannot fit at all, is cut with the `[truncated: ...]` note. Found by
  the existing `agent.e2e` DOM Health tests, which read the result as JSON.
- DOM Health reports (`run_dom_health_audit`,
  `run_application_dom_health_audit`) get a 12,000-token ceiling instead of
  2,000: the system prompt tells the model to report them exactly as
  returned. Measured in `dom-health-apps.e2e` fixtures: 9,177 to 70,886
  characters (about 2.3k to 17.7k tokens); the tests that read report details
  need up to 42,942 characters. With the 2,000 cap, 8 existing DOM Health e2e
  tests failed.
